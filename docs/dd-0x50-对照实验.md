# DD 驱动 0x50 · 对照实验方案

**目的**：验证「程序退出后驱动仍驻留内核 → 野指针迟到写入 → 0x50」这条链路，并确认
「退出后主动卸载驱动（`sc stop`）」能否拆掉这颗雷。

**为什么值得先做实验**：把卸载逻辑写进发布版是一次**不可回退的行为变更**——万一卸载时机
不对（带着打开的句柄直接停驱动），会把「几十秒后崩」变成「退出瞬间崩」。先用两条命令验证，
比改代码再验证快得多，也没有发布风险。

**不需要改任何代码，全程约 15 分钟。**

---

## 前提

1. 这台机器上**只有衍天高手**在用 DD 驱动。如果有万象、按键精灵、其他连发/宏工具同时在跑，
   它们会共用同一个 `dd63330` 服务——实验期间请先全部退出，否则结论无法归因。
2. 先保存好手头工作。实验期间可能反复蓝屏。
3. 全程用**管理员**命令行（开始菜单搜 `cmd` → 右键「以管理员身份运行」）。
4. 每次实验前确认系统已重启过一次（干净起点，避免上一轮残留干扰）。

---

## 第 0 步 · 不用蓝屏也能验证前提（先做这个）

```
:: 1. 打开衍天高手，等待 10 秒（让驱动完整初始化）
:: 2. 关闭衍天高手
:: 3. 立刻执行：
sc query dd63330
```

看 `STATE` 那一行：

| 结果 | 含义 |
|---|---|
| `4 RUNNING` | **驱动确实还在核心里**——前提成立，继续做对照实验 |
| `1 STOPPED` / 提示服务不存在 | 驱动已退出，这条链路不成立，直接看文末「结论 C」 |

再补一条，看它能不能干净卸载（**这一步在程序已退出后做，不要在程序还开着时做**）：

```
sc stop dd63330
sc query dd63330
```

- `sc stop` 报成功、`sc query` 变成 `STOPPED` → 驱动支持优雅卸载，后面的修复方向可行
- `sc stop` 报成功但 `sc query` 仍是 `RUNNING` → 卸载被未释放的句柄/引用卡住，这是另一条重要线索
- `sc stop` 报错（1052 / 1051 等）→ 记下错误码

## 对照实验（每组 3 次，交替做）

**A 组 · 对照（什么都不做）**

1. 打开衍天高手，等 10 秒
2. 关闭
3. **不做任何操作**，静置观察 3 分钟
4. 记录：是否蓝屏、关掉后大约多少秒

**B 组 · 干预（退出后立刻卸载驱动）**

1. 打开衍天高手，等 10 秒
2. 关闭
3. **5 秒内**执行 `sc stop dd63330`
4. 静置观察 3 分钟
5. 记录：`sc stop` 是否成功、是否蓝屏、关掉后大约多少秒

> 顺序建议 A-B-A-B-A-B。每次蓝屏后重启，等系统稳定 2 分钟再做下一轮。

## 判据

| 观察结果 | 结论 | 下一步 |
|---|---|---|
| A 组 3/3 崩，B 组 0/3 崩 | 卸载能拆雷 | 值得把「退出时卸载驱动」做进程序（带开关，先只在问题机器开） |
| A 组 3/3 崩，B 组仍崩 | 雷在驱动内部更早的位置（不在客户端清理路径上） | 卸载无效，只能「不加载」或等作者修 |
| A、B 两组都不崩 | 复现条件没抓到 | 回到客户现场：当时在跑什么游戏/反作弊、程序连续开了多久、是不是只有长时间运行后才崩 |
| 第 0 步就显示 STOPPED | 驱动不驻留，链路不成立 | 重点转向「运行期间」的 UAF（需要更长运行时间的复现） |

> 注意：即使 B 组有效，它也只覆盖「用户正常退出」。任务管理器强杀、程序崩溃、直接断电，
> 驱动一样会攥着野指针留在核心里——这部分只能靠「不加载」或驱动作者修复。

---

## 实验后恢复

不用手动恢复：衍天高手下次启动时会自己 `StartService`（服务项仍是按需启动）。
确认方式：开一次程序，`sc query dd63330` 应回到 `RUNNING`。

---

## 结论 C · 如果驱动不驻留

那说明崩溃发生在**运行期间**，请补充采集：程序连续运行多久崩、崩的时候正在做什么操作
（连发中 / 空闲 / 切换模式）、是否开着游戏或反作弊。这类信息决定下一轮往哪儿查。
